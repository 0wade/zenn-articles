## はじめに

Web開発をしていると「CORSエラーが出た」「セッションが切れた」という言葉をよく耳にします。しかしこれらの仕組みを「なんとなく」でしか理解できていないと、エラーの原因がわからなかったり、セキュリティ上の設定ミスを引き起こしたりすることがあります。

この記事では **オリジン・同一オリジンポリシー・CORS・セッション・ブラウザのプロセスモデル** を順番に整理し、実務で注意すべきポイントもまとめます。

---

## オリジン（Origin）とは

オリジンとは **「スキーム + ホスト + ポート」の3点セット** のことです。

```
https://example.com:443/path?query=1
└─────┘ └─────────┘ └──┘
スキーム   ホスト     ポート  ← この3つがオリジン
```

パス（`/path`）やクエリパラメータ（`?foo=bar`）はオリジンに**含まれません**。

### 同一オリジンかどうかの判断例

| URL | オリジン | `https://example.com` と同一? |
|---|---|---|
| `https://example.com/a` | `https://example.com:443` | ✅ |
| `https://example.com/b` | `https://example.com:443` | ✅ |
| `http://example.com` | `http://example.com:80` | ❌ スキームが違う |
| `https://sub.example.com` | `https://sub.example.com:443` | ❌ ホストが違う |
| `https://example.com:8080` | `https://example.com:8080` | ❌ ポートが違う |

「同じドメインでもサブドメインが違えば別オリジン」という点は見落としやすいので注意が必要です。

---

## 同一オリジンポリシー（Same-Origin Policy）

ブラウザには「**別のオリジンへのアクセスを制限する**」という安全装置が組み込まれています。これを **同一オリジンポリシー** といいます。

### なぜ必要なのか

次のような攻撃シナリオを考えてみます。

```
1. あなたが悪意あるサイト（evil.com）を開く
2. evil.com 内の JavaScript が your-bank.com にリクエストを送ろうとする
3. ブラウザ「オリジンが違う！このリクエストはブロックする！」
```

もしこの制限がなければ、あなたが銀行サイトにログイン済みの状態で悪意あるサイトを開くだけで、Cookie が悪用されて不正なリクエストが飛んでしまいます。同一オリジンポリシーはこれを防ぐための仕組みです。

### 重要な補足

同一オリジンポリシーは **ブラウザの制約** です。`curl` やサーバーサイドのコードからは制限されません。

---

## CORS（Cross-Origin Resource Sharing）

同一オリジンポリシーは安全ですが、**正当な理由で別オリジンと通信したい**場面もあります。

例えば、フロントエンドが `https://app.example.com` でAPIが `https://api.example.com` の場合、オリジンが異なるため通常はブロックされます。

CORSはこのような場合のための**公式の許可システム**です。サーバーが「このオリジンからのアクセスは許可する」と明示的に宣言することで、ブラウザが通信を許可します。

### シンプルリクエストの場合

`GET` や `Content-Type: application/x-www-form-urlencoded` な `POST` など、条件を満たすシンプルなリクエストは次のように処理されます。

```
ブラウザ → api.example.com
リクエスト:
  GET /data HTTP/1.1
  Origin: https://app.example.com   ← ブラウザが自動付与

サーバー → ブラウザ
レスポンス:
  Access-Control-Allow-Origin: https://app.example.com  ← 許可！
```

ブラウザはレスポンスの `Access-Control-Allow-Origin` を確認し、自分のオリジンが含まれていれば結果を JavaScript に渡します。含まれていなければ**CORSエラー**としてブロックします。

### プリフライトリクエスト（Preflight）

`PUT` / `DELETE` メソッドや、`Authorization` などのカスタムヘッダーを使うリクエストは「複雑なリクエスト」に分類されます。この場合、ブラウザはまず **「本番リクエストを送っていいですか？」という事前確認（Preflight）** を行います。

```
Step 1: ブラウザ → サーバー（事前確認、OPTIONSメソッド）
  OPTIONS /data HTTP/1.1
  Origin: https://app.example.com
  Access-Control-Request-Method: PUT
  Access-Control-Request-Headers: Authorization

Step 2: サーバー → ブラウザ（許可の返答）
  Access-Control-Allow-Origin: https://app.example.com
  Access-Control-Allow-Methods: PUT
  Access-Control-Allow-Headers: Authorization

Step 3: ブラウザ → サーバー（本番リクエスト送信）
  PUT /data HTTP/1.1
  Authorization: Bearer xxxxx
```

### 主なCORSレスポンスヘッダー

| ヘッダー | 意味 |
|---|---|
| `Access-Control-Allow-Origin` | 許可するオリジン（`*` で全オリジン許可） |
| `Access-Control-Allow-Methods` | 許可するHTTPメソッド |
| `Access-Control-Allow-Headers` | 許可するリクエストヘッダー |
| `Access-Control-Allow-Credentials` | Cookie などの認証情報送信を許可するか |
| `Access-Control-Max-Age` | Preflight の結果をキャッシュする秒数 |

## セッション（Session）

HTTPは**ステートレス（状態を持たない）**なプロトコルです。リクエストを2回送っても、サーバーは「同じ人からの2回目」とは認識できません。

セッションはこの問題を解決する仕組みで、「**一連のやり取りを同一ユーザーのものとして紐づける**」ものです。

### ① セッションID方式（サーバーサイドセッション）

```
1. ログイン
   → サーバーがセッションIDを発行し、サーバー側のストレージに状態を保存
   → Cookie にセッションIDを書き込んでブラウザに渡す

2. 以降のリクエスト
   → ブラウザが Cookie を自動送信
   → サーバーがセッションIDを照合して「誰のリクエストか」を特定
```

セッションの実体はサーバー側にあり、Cookie はあくまで「鍵（ID）」にすぎません。

### ② トークン方式（JWTなど）

```
1. ログイン
   → サーバーがトークン（ユーザー情報を含む暗号署名済み文字列）を発行
   → ブラウザがトークンを保存（LocalStorage または Cookie）

2. 以降のリクエスト
   → Authorization ヘッダーにトークンを付与して送信
   → サーバーは署名を検証するだけ（サーバー側に状態を持たない）
```

サーバー側にセッション情報を持たないため、**スケールアウトがしやすい**のがメリットです。

## プロセス（ブラウザのプロセスモデル）

CORSやセッションを理解する上で関連するのが、ブラウザの**マルチプロセス構造**です。

Chromeなどのモダンブラウザは、タブ・オリジンごとに**別プロセスを起動**します（Site Isolation）。

```
Chrome
├── ブラウザプロセス（UI・タブ管理）
├── レンダラープロセス（example.com タブ）
├── レンダラープロセス（evil.com タブ）  ← 別プロセスで完全分離
└── GPUプロセス
```

このアーキテクチャにより、あるタブが別タブのメモリを直接読み取る攻撃（Spectreなどのサイドチャネル攻撃）を防いでいます。同一オリジンポリシーと合わせて、Webの安全性を支える基盤の一つです。

## 実務での注意点

### CORSに関する注意点

**`Access-Control-Allow-Origin: *` を安易に使わない**

`*`（ワイルドカード）は「すべてのオリジンを許可する」という設定です。公開APIなら問題ありませんが、認証が必要なAPIに使うのは危険です。また、後述の Cookie 送信との組み合わせでは仕様上使えません。

**Cookie を送る場合は設定が2か所必要**

CORS通信で Cookie を送信するには、**サーバー側とクライアント側の両方**の設定が必要です。片方だけでは動きません。

```
# サーバー側（レスポンスヘッダー）
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://app.example.com  # * は使えない

# クライアント側（fetch の場合）
fetch('https://api.example.com/data', {
  credentials: 'include'  // これが必要
})
```

**CORSエラーはブラウザが止めている**

CORSエラーが発生しても、サーバーにはリクエストが届いていることが多くあります（ブラウザがレスポンスを受け取った後に捨てる）。デバッグ時はサーバーのログも確認しましょう。

**Preflightのキャッシュを設定する**

`Access-Control-Max-Age` を設定しておくと、ブラウザが Preflight の結果をキャッシュし、毎回 `OPTIONS` リクエストを送らなくなります。パフォーマンス改善に有効です。

```
Access-Control-Max-Age: 86400  # 24時間キャッシュ
```

---

### セッションに関する注意点

**Cookie には必ずセキュリティ属性を設定する**

| 属性 | 効果 |
|---|---|
| `HttpOnly` | JavaScriptから読み取れなくする（XSS対策） |
| `Secure` | HTTPS通信のみで送信される（通信の盗聴対策） |
| `SameSite=Strict` または `Lax` | 別サイトからのリクエストに Cookie を付けない（CSRF対策） |

これらをすべて設定するのが基本です。

**ログイン後はセッションIDを再発行する（セッション固定攻撃対策）**

ログイン前に発行されたセッションIDをログイン後もそのまま使い続けると、攻撃者がそのIDを事前に仕込んでおくことでセッションを乗っ取れてしまいます（セッション固定攻撃）。ログイン成功後は必ず新しいセッションIDを発行しましょう。

**JWTの保存場所はトレードオフがある**

| 保存場所 | XSSへの耐性 | CSRFへの耐性 | 備考 |
|---|---|---|---|
| LocalStorage | ❌ 弱い（JSで読める） | ✅ 強い | SPA でよく使われるが注意が必要 |
| HttpOnly Cookie | ✅ 強い（JSで読めない） | ❌ 弱い | `SameSite` と組み合わせて対策する |

どちらにもリスクがあります。脅威モデルに合わせて選択し、それぞれの弱点に対策を施すことが重要です。

---

## まとめ

- **オリジン** = スキーム + ホスト + ポートの3点セット。パスは含まない
- **同一オリジンポリシー** = 別オリジンへのアクセスをブラウザが制限する安全装置
- **CORS** = サーバーが「このオリジンは許可する」と宣言することで制限を緩和する仕組み
- **セッション** = ステートレスなHTTPで「同一ユーザーの一連のやり取り」を維持する仕組み
- **ブラウザのプロセス分離** = オリジンごとにプロセスを分けてメモリを守る構造

これらはすべて「Webの安全」を守るために連携して機能しています。設定ミスや理解不足がセキュリティホールに直結するため、一つひとつ正確に把握しておくことが大切です。
