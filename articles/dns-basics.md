## はじめに

ブラウザで `https://example.com` と入力したとき、コンピュータは最初に「example.com というドメイン名が、どのIPアドレスに対応するか」を調べます。この仕組みが **DNS（Domain Name System）** です。

前回の TCP/IP の記事で「① DNS でドメイン → IPアドレスに変換」とサラッと触れましたが、この変換の裏側にはかなり複雑な仕組みがあります。この記事では DNS の全体像を、実務での注意点も交えて丁寧に解説していきます。

---

## DNS とは何か

**DNS（ドメインネームシステム）** は、人間が読みやすいドメイン名（`example.com`）をコンピュータが使うIPアドレス（`93.184.216.34`）に変換する仕組みです。

> **アナロジー**：電話帳のようなものです。名前（ドメイン）から電話番号（IPアドレス）を調べる、というイメージです。

IPアドレスを直接覚えて使うのは現実的ではないため、DNS が「名前 ↔ IPアドレス」の対応を管理しています。

---

## DNS の名前解決の流れ

`example.com` のIPアドレスを調べる際、以下の登場人物が関わります。

| 登場人物 | 役割 |
|----------|------|
| **スタブリゾルバ** | ブラウザなど、クライアント側で最初にDNS問い合わせを投げる部分 |
| **フルサービスリゾルバ**（キャッシュリゾルバ） | ISP や社内DNSサーバー。実際に問い合わせを代行してくれる |
| **ルートネームサーバー** | DNS の頂点。TLD（`.com` など）の場所を教える |
| **TLD ネームサーバー** | `.com` `.jp` などのドメイン管理。権威サーバーの場所を教える |
| **権威ネームサーバー** | ドメインの実際のIPアドレスを持つ最終回答者 |

### 名前解決のステップ

```
ブラウザ（スタブリゾルバ）
    │
    │ ① "example.com のIPを教えて"
    ▼
フルサービスリゾルバ（ISP や社内DNSサーバー）
    │                           ↑
    │ ② "example.com のIPを教えて"       ⑦ "93.184.216.34 です"
    ▼                           │
ルートネームサーバー（13系統）
    │
    │ ③ ".com の TLD サーバーは xxx.xxx.xxx.xxx です"
    ▼
TLD ネームサーバー（.com 担当）
    │
    │ ④ "example.com の権威サーバーは yyy.yyy.yyy.yyy です"
    ▼
権威ネームサーバー（example.com 担当）
    │
    │ ⑤ "example.com = 93.184.216.34 です"
    ▼
フルサービスリゾルバ（結果をキャッシュして返す）
    │
    │ ⑥ "93.184.216.34 です"
    ▼
ブラウザ → TCP 接続開始
```

一見複雑に見えますが、実際には後述するキャッシュのおかげで多くの場合このすべてのステップは踏みません。

### 各ステップの詳細

**① スタブリゾルバからの問い合わせ**

ブラウザがドメインを解決したいとき、OS に組み込まれたスタブリゾルバが動きます。スタブリゾルバはまず自分のキャッシュを確認し、なければフルサービスリゾルバへ問い合わせます。

**② フルサービスリゾルバが代わりに調べる**

フルサービスリゾルバは「再帰的問い合わせ（Recursive Query）」を行います。クライアントの代わりにルートから順番に辿って最終回答を取得し、クライアントへ返します。

**③〜⑤ 反復問い合わせ（Iterative Query）**

フルサービスリゾルバは、ルート → TLD → 権威サーバーと「次の担当者」を紹介されながら問い合わせを繰り返します。これを反復問い合わせと呼びます。

## DNS のレコード種別

権威ネームサーバーが持つ情報は **リソースレコード** と呼ばれ、用途によって種類が異なります。

| レコード種別 | 内容 | 例 |
|------------|------|-----|
| **A** | ドメイン → IPv4アドレス | `example.com → 93.184.216.34` |
| **AAAA** | ドメイン → IPv6アドレス | `example.com → 2606:2800:21f:...` |
| **CNAME** | ドメイン → 別のドメイン（エイリアス） | `www.example.com → example.com` |
| **MX** | メールサーバーの指定 | `example.com のメールは mail.example.com へ` |
| **TXT** | 任意のテキスト情報 | SPF・DKIM・ドメイン所有確認など |
| **NS** | そのドメインのネームサーバー | `example.com の NS は ns1.example.com` |
| **PTR** | IPアドレス → ドメイン（逆引き） | `93.184.216.34 → example.com` |

## TTL とキャッシュの仕組み

### TTL（Time To Live）とは

DNS レコードには **TTL（有効期限）** が設定されています。フルサービスリゾルバは取得した結果を TTL が切れるまでキャッシュし、同じ問い合わせが来たときはキャッシュを返します。

```
TTL = 3600 の場合

取得した瞬間：残り 3600 秒キャッシュ保持
1時間後     ：キャッシュ失効 → 次の問い合わせ時に再度フルサービスリゾルバがルートから調べる
```

### キャッシュのメリット

- DNS サーバーへの問い合わせ回数が減る → レスポンスが速くなる
- 上位の DNS サーバーの負荷が下がる

### キャッシュの場所（複数のレイヤー）

```
① ブラウザのキャッシュ（Chrome なら chrome://net-internals/#dns で確認可）
② OS のキャッシュ（hosts ファイルも含む）
③ フルサービスリゾルバのキャッシュ（ISP や社内DNSサーバー）
```

## ルートネームサーバーについて

「ルートネームサーバーは世界に13系統しかない」と聞くと「それって壊れたらインターネット全体が止まるのでは？」と思うかもしれません。

実際には、13系統というのは **IPアドレスの数（論理的な数）** です。それぞれが **Anycast（エニーキャスト）** という技術を使い、世界中に数百台のサーバーを物理的に分散配置しています。どこからアクセスしても最も近いサーバーに自動的に誘導される仕組みです。

---

## 実務での注意点

### ① TTL を短くしすぎない・長すぎない

TTL は DNS の移行時に特に重要です。

| TTL 設定 | メリット | デメリット |
|----------|----------|-----------|
| 短い（例：60秒） | IPアドレス変更がすぐ反映される | DNS サーバーへの問い合わせが増える（負荷・コスト増） |
| 長い（例：86400秒＝1日） | キャッシュが効いて高速・負荷少 | IPアドレスを変更してもすぐ反映されない |

**ベストプラクティス：サービス移行の数日前から TTL を短く（300〜600秒など）設定し、移行後に元の長い TTL に戻す。**

### ② DNS 伝播（DNSプロパゲーション）に時間がかかる

DNS レコードを変更しても、世界中のキャッシュが更新されるまで時間がかかります（最大で TTL 分）。この現象を **DNS 伝播（Propagation）** と呼びます。

「ドメイン変えたのにまだ古いサーバーに繋がる！」という問い合わせは多くの場合これが原因です。`dig` コマンドや DNS チェックツールで伝播状況を確認できます。

```bash
# 特定の DNS サーバーに問い合わせる（8.8.8.8 は Google のDNS）
dig example.com @8.8.8.8

# TTL の確認
dig example.com | grep -i ttl
```

### ③ hosts ファイルは最優先される

OS の `hosts` ファイルに記述がある場合、DNS よりも優先されます。

```
# Windows: C:\Windows\System32\drivers\etc\hosts
# Mac/Linux: /etc/hosts

127.0.0.1 localhost
192.168.1.10 myapp.local  ← この行があると DNS を使わず直接このIPに繋ぐ
```

ローカル開発環境での動作確認によく使われますが、古い設定が残っていると「DNSを変えたのに繋がらない」原因になることがあります。

### ④ DNS キャッシュポイズニング（セキュリティ上の注意）

**DNS キャッシュポイズニング** とは、攻撃者が偽の DNS レスポンスをキャッシュリゾルバに注入し、ユーザーを偽サイトに誘導する攻撃です。

```
正常なDNS問い合わせ
ユーザー → DNSリゾルバ → 権威サーバー → 正しいIP

キャッシュポイズニング後
ユーザー → DNSリゾルバ（偽のIPがキャッシュされている） → 攻撃者のサーバー
```

これを防ぐために **DNSSEC（DNS Security Extensions）** という署名による検証の仕組みがあります。また、DNS over HTTPS（DoH）や DNS over TLS（DoT）を使うと、通信自体を暗号化できます。

### ⑤ 内部 DNS と外部 DNS のスプリット設定

企業環境では、社内からのアクセスと社外からのアクセスで異なるIPアドレスを返す **スプリットホライズン DNS（Split-horizon DNS）** という設定がよく使われます。

```
社内ネットワークから api.example.com にアクセス
  → 内部 DNS → プライベートIP（192.168.x.x）を返す

社外（インターネット）から api.example.com にアクセス
  → 外部 DNS → グローバルIP を返す
```

これにより、社内通信はプライベートネットワーク経由にでき、セキュリティとパフォーマンスの両立ができます。

### ⑥ CNAME と A レコードの使い分け

| 状況 | 推奨レコード |
|------|-------------|
| `www.example.com` を `example.com` の別名にしたい | CNAME |
| IPアドレスを直接指定したい | A レコード |
| ルートドメイン（`example.com` 自体）の設定 | **CNAME は使えない**（A レコードまたは ALIAS/ANAME） |

ルートドメインに CNAME を使うと DNS の仕様違反になります。これは多くのサービスで設定ミスとして引っかかりやすいポイントです。

## よく使う DNS 確認コマンド

```bash
# ドメインのIPアドレスを確認（シンプル）
nslookup example.com

# 詳細情報を確認
dig example.com

# 特定のレコード種別を確認
dig example.com MX     # メールサーバー
dig example.com TXT    # TXTレコード
dig example.com NS     # ネームサーバー

# 逆引き（IPからドメインを調べる）
dig -x 93.184.216.34

# 特定のDNSサーバーに問い合わせる（Google DNS: 8.8.8.8）
dig example.com @8.8.8.8
```

Windows の場合は `nslookup` が標準で使えます。Linux/Mac では `dig` がより詳しい情報を得られます。

---

## まとめ

- **DNS** はドメイン名をIPアドレスに変換する「インターネットの電話帳」
- 名前解決は **スタブリゾルバ → フルサービスリゾルバ → ルート → TLD → 権威サーバー** の順に行われる
- **TTL** が設定されており、各リゾルバはその期間だけキャッシュを保持する
- キャッシュのレイヤーは「ブラウザ → OS → リゾルバ」の3段階ある
- 実務では **TTL 管理・DNS 伝播・hosts ファイル・スプリット設定** に注意が必要
- セキュリティ面では **キャッシュポイズニング** に注意し、DNSSEC や DoH/DoT で対策できる
- ルートドメインに CNAME を使うのは仕様違反なので注意
